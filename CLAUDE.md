# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

See [GameDesign.md](GameDesign.md) for the game concept. In short: a city-builder/roguelike where you manage baby turtles that hatch from a nest on an island, collecting resources to protect their unhatched siblings from ocean-washed trash.

A run is a repeating day/storm loop against an offshore garbage patch that loses one health segment per storm survived. Deplete it and the run ends as a **win**; let trash reach the nest and it ends as a **loss**. Either way the run's score is banked as permanent XP, which levels the player up and unlocks opt-in **run modifiers** for future runs.

## Tech stack

- Unity **6000.5.2f1** (Unity 6), 2D project using the Universal Render Pipeline (URP 2D Renderer).
- New Input System (`UnityEngine.InputSystem`) — all scripts read `Mouse.current`/`Keyboard.current` directly, not the legacy `Input` class.
- TextMeshPro for UI text.
- Notable packages (see `Packages/manifest.json`): 2D Animation, Aseprite importer, PSD importer, Sprite Shape, Tilemap (+ extras), Timeline, Visual Scripting, Unity Test Framework.

## Working with this repo

- This is a Unity project opened and run through the Unity Editor — there's no CLI build script or package.json here yet.
- **To typecheck a script change without the Editor**, build the generated project: `dotnet build Assembly-CSharp.csproj`. It resolves the Unity managed DLLs by absolute path and catches real compile errors in seconds. Expect ~11 pre-existing `CS0649` warnings on `[SerializeField]` fields inside `[System.Serializable]` structs — those are normal, only new errors matter.
- Unity's Test Framework package is installed but no tests have been written; when they exist, they run via the Editor's Test Runner (Window > General > Test Runner) or Unity's `-runTests -batchmode` CLI mode.
- `Library/`, `Temp/`, `Logs/`, and `UserSettings/` are Unity-generated caches, not source — never edit or rely on their contents.
- Scenes live in `Assets/Scenes`; render pipeline / input / volume config lives in `Assets/Settings`; all gameplay code is under `Assets/Scripts`.
- Only write/edit `.cs` scripts. Scene, prefab, and Inspector wiring (new GameObjects, assigning serialized fields, adding components in the Editor) must be described as steps for the user to do themselves — don't attempt to edit `.unity`/`.prefab` YAML directly.

## Architecture

### Scene-wide singletons, no dependency injection

Turtles, trash, and upgrade cards are all runtime-instantiated (spawned from prefabs, not placed in the scene), so they can't hold a pre-wired scene reference the way hand-placed objects can. Instead, core systems expose themselves as `public static X Instance` set in `Awake`/`OnEnable` and cleared in `OnDestroy`/`OnDisable`, and everything else reaches them via the static accessor: `ResourceManager.Instance`, `UpgradeManager.Instance`, `PathfindingManager.Instance`, `BuildModeController.Instance`, `TurtleNest.Instance`, `ScoreManager.Instance`, `DayStormCycle.Instance`, `GameModifierManager.Instance`, `GarbagePatch.Instance`, `TrashSpawner.Instance`, `AudioManager.Instance`, `SettingsMenuUI.Instance`. When adding a new manager-style system that runtime-spawned objects need to reach, follow this same pattern rather than introducing a new wiring mechanism.

Alongside the singletons, several types keep a **static registry of every live instance** so other systems can sweep them without a scene walk: `TurtleAgent.AllTurtles`, `TrashHealth.AllTrash`, `ResourceNode.AllNodes`, `BuildingHealth.AllBuildings`, `TurtleBed.AllBeds`, `SandPile.AllSandPiles`, `Coconut.AllCoconuts`, `JellyfishAgent.AllJellyfish`, `CoralReef.AllReefs`. Registration is always `OnEnable`/`OnDisable`.

### Static flags for cross-system gating

Instead of an event bus, mutually-exclusive "modes" are coordinated by static bools that every interested system polls each frame: `DayStormCycle.IsStorming` (day vs. storm phase — gates harvesting, resource respawn, aggro), `BuildModeController.IsActive` (build mode — the drawer latched open by its hammer tab, the only way in; `IsToggledOpen` is the live latch that flag is refreshed from each frame, and `IsBlockedByPhase` is the shared "a phase owns the screen" condition that forces both off), `UpgradeSelectionUI.IsActive` (end-of-storm card picker), `GarbagePatchCutsceneController.IsActive` (the patch-hit camera pan, and everything after a win), `TutorialManager.IsActive` (scripted tutorial, which also freezes the day clock), `GameOverUI.IsPaused`/`IsRunOver`, `SettingsMenuUI.IsOpen` (the settings screen, which is modal and pauses gameplay behind it — folded into `IsBlockedByPhase` rather than listed beside each phase, so everything that already stands down for a blocking phase covers it for free). `TurtleSelectionController`, `CameraController` and `BuildModeController` all stand down while any of these is up; `TurtleAgent` reads `IsStorming` directly rather than being told about transitions via a callback.

### Island generation → downstream systems

`IslandGenerator` procedurally builds three tilemaps (Water fills everything, ShallowWater rings the coast, Sand is land-only) from `IslandNoiseMap`'s blob-chain noise field, forces the map center to land, and discards every landmass not connected to it — so there's always exactly one island, however abstract its shape.

Shape is subtracted from at two different stages, and the distinction is the point of having both. The **crescent bite** (`GenerateBlobField`) is chance-weighted and subtracts from the shape *field*, before thresholding, calibration and smoothing — so how much land it costs is emergent and varies run to run. **`IslandNoiseMap.CarveChunks`** runs last, on the finished single-landmass *mask*, and removes an exact authored tile count split across N contiguous chunks, each grown one tile at a time from a (usually coastal) seed cell. It protects the nest's center disc, floors how small the island can get, carries a chunk's shortfall to the next one so the total is always delivered, and hands back the mask of what it took — which `IslandGenerator` reuses to keep carved water **shallow**, since `TrashSpawner` scores its clusters by closeness to map center and would otherwise treat a carved lagoon as the best spawn site on the map. Run `KeepIslandContainingCenter` again after carving; it's what discards a limb the carve severed.

The three tilemaps are **not** three stacked sheets: Water holds the ocean only, and land/shallow cells are left EMPTY on it. That emptiness is load-bearing. A Rule Tile only ever sees its own tilemap, so leaving those cells empty is the only way the ocean's shoreline ring can tell where the water stops — nothing else on the Water tilemap could say it. Every consumer already reads that map through a "water AND NOT sand AND NOT shallow" test (`IsDeepWater`, `TrashSpawner`) and so is unaffected; the exception is `PathfindingManager`, which takes its A* search bounds from `cellBounds` and therefore needs the map's *extent* rather than its contents — which is why the border frame is painted unconditionally even where it's invisible.

The ocean itself is deliberately **two** tiles on that one tilemap: `OceanRuleTile` in a narrow band hugging the coast (`Ocean Ring Width`, mask built by `BuildOceanRingMask`), and a plain Tile for the open sea and the whole outskirts rectangle. Making all of it a Rule Tile would evaluate eight neighbours per cell across tens of thousands of cells for a sprite that never varies. The mix only works because `OceanRuleTile` matches on **occupancy** — any tile is "this", only an empty cell is not — which is exact precisely because the Water tilemap holds nothing but ocean. Give that band a stock `RuleTile` instead and it tests `other == this`, reads the plain tile beside it as land, and rings itself with a second coastline facing the open sea. **Rule tiles need `RefreshAllTiles` after a bulk `SetTilesBlock`**, since a block set fills in the neighbours a tile already chose its sprite from.

It fires `IslandGenerated` once tiles are painted and the nest is spawned at the origin; `PathfindingManager` (invalidates its deep-water cache), `DayStormCycle` (starts the first day), `UpgradeManager` (replays per-island respawns), `StarterTurtleBedSpawner`, `GarbagePatchSpawner` and the scenery/resource spawners all subscribe to this event rather than being called in a fixed order from a bootstrapper.

### Day/storm loop

`DayStormCycle` drives the core game loop: a fixed-length day phase, then a storm where `TrashSpawner.SpawnRound` scatters trash in open deep water using an exponentially-growing "rating budget" (each `TrashDefinition` costs a rating; the budget determines both volume and which trash tiers can afford to appear). The storm ends once `TrashSpawner.AnyTrashAlive()` is false, at which point buildings heal and `UpgradeSelectionUI` offers a card pick before the next day begins — `IsStorming` deliberately stays `true` through that pick so turtles don't resume daytime behavior while the player is still choosing.

Right after that pick, `GarbagePatchCutsceneController` pans out to the offshore `GarbagePatch`, knocks off one health segment, and pans back — zooming to frame the patch at its live size (`GarbagePatch.MeasureVisualRadius`, since the pile is eaten away from the outside in over a run) and restoring the player's own zoom on the way home. Landing back home is also what ends the weather, via `AmbienceController.EndStormWeather`: `IsStorming` stays true through all of this, so the rain has to be told directly rather than left to poll it. Once the patch depletes, it shows the win screen (`GameOverUI.ShowWin`) and deliberately never invokes its `onComplete`, so `DayStormCycle` stays parked and never spawns another round.

### TurtleAgent: standing objective + transient detours

`TurtleAgent` (`Assets/Scripts/Turtle/TurtleAgent.cs`) is by far the largest and most central script. Its model: a **target resource objective** (a resource *type*, set only by the player via `MoveToResource`) is a standing order nothing else may clear. Every other behavior — `MoveToPoint`, `MoveToBuilding`, a storm-triggered aggro chase against nearby trash, parking at a Watchtower — is a transient detour layered on top; once it ends, the turtle falls back through `Update()`'s own day/night default (seek the objective by day, nest-guard/wander by night) evaluated fresh rather than restored from a snapshot. **Read the file's class-level doc comment before modifying turtle behavior** — it explains why no interruption needs save/restore logic.

Turtles physically pass through non-interactable buildings but switch onto a dedicated `TurtleInteracting` physics layer while targeting an interactable one (a Rune, a Watchtower), so a "bump to interact" collision can register without turtles generally getting stuck on walls.

Contact is head-only: `TurtleHeadHitbox` on the Head child relays `OnTriggerEnter2D` to `TurtleAgent.HandleHeadHit`, and reloads its own collider once per fin stroke so a mashed contact keeps re-firing. A non-zero `Max Reload Interval` adds a timer-driven reload on top, which is how crabs attack faster than they swim.

### Speed buffs compose as independent multiplier layers

`TurtleLocomotion` holds one field per source of speed change — permanent upgrades, Campfire, the temporary food buff, a glue slow, Algae, Barnacles — each with its own `Set*` setter that **overwrites** (callers always pass an already-cumulative total). `RecalculateBuffSpeedMultiplier` multiplies them all into one product pushed to fin stroke rate and turn rate. A new speed source means a new layer and a new term in that product; never mutate `impulseForce`, which is reserved for the idle-amble slowdown — a bigger lunge per stroke flings a turtle off course.

### Data-driven extensibility: definitions on prefabs, not new code

New building types, upgrade cards and run modifiers are meant to be added as prefabs, not new manager code:
- `BuildableDefinition` (name, resource cost, price-scaling-per-placement) attaches to any building prefab; `BuildModeController` reads it generically to show the ghost, check affordability, and instantiate on placement. Optional `IHasPlacementRange` adds a live range-preview circle under the ghost.
- `UpgradeCardDefinition` is an abstract base with an `Apply()` override; concrete cards live under `Assets/Scripts/Upgrades/` and are referenced by `UpgradeSelectionUI`'s upgrade pool array. `Apply()` is called **on the prefab asset itself, never an instance** — so no `Awake`/coroutines/serialized scene references, and no per-run mutable state; reach the scene through singletons or `FindAnyObjectByType`.
- Two gates keep branch cards out of the pool until earned: `IRequiresBuilding` (parent is a buildable — checked against `BuildModeController.IsUnlocked`) and `IRequiresUpgrade` (parent is a plain upgrade — each card answers `IsPrerequisiteMet` from `UpgradeManager` state, so no prefab wiring). `UpgradeSelectionUI.Show` checks both.
- `GameModifierDefinition` is the run-modifier equivalent, and deliberately has no `Apply()` of its own — its effect is whichever `UpgradeCardDefinition` components sit alongside it on the same prefab, reused verbatim.
- `RuneEffect` is the base for rune buildings (`FlipperRune`, `HardHatRune`): a turtle bumps it repeatedly via `TurtleHeadHitbox` → `TurtleAgent.HandleHeadHit` → `RuneEffect.RegisterHit`, and once one turtle's hit count crosses `hitsRequired` it gets an indefinite buff through the same `ApplyBuff`/`AlreadyHasBuff` override pair new runes must implement.
- `ResourceRespawnBooster` is one script serving three prefabs (Fertilizer, Pet Rock, Algae) via a `BoosterKind` enum that selects which upgrade track it reads live.
- `DemolishTool` is the drawer's **demolish entry**, and rides the same mechanism from the other side: a prefab carrying a `BuildableDefinition` (empty cost) that is never placed, so it draws as a drawer row and a cursor ghost for free, and `BuildModeController` branches on the component in exactly three places (resolve it on selection, target a building instead of a cell, demolish instead of place). Like an upgrade card it runs **on the prefab asset** — no `Awake`, no coroutines, which is why its refund flies out as one burst rather than a staggered stream. It refunds a fraction of `BuildableDefinition.PaidCost` — what that instance actually cost, recorded at placement, *not* the live `Cost`, which is the scaled-up price of the *next* one — and delivers it to the nest on the turtles' own `ResourcePopEffect`, deliberately without awarding score (that was paid at harvest; paying it again would make build-and-demolish a score farm). `BuildSelectionUI` floats the entry to the top of the list with an extra gap below it; put it **last** in `Buildables`, since array order is scroll order and index 0 is what build mode opens on. What may be demolished is `BuildModeController.CanDemolish`, checked inside `FindDemolishTarget` rather than at the click so the highlight and the click can't disagree — its one rule is `Min Turtle Beds`, since beds are the only source of turtles and a run with none is unwinnable. It binds demolition only; a bed lost to trash is a loss the storm earned.

A card that spawns something physical into the world must also register a `UpgradeManager.RegisterPerIslandRespawn` action, so it survives a map regeneration (see `SeaweedUpgradeCard`, `CoralReefUpgradeCard`, `CrabRecruitUpgradeCard`).

### Resources: turtles deliver everything to the Nest; food comes back out as a night buff

`ResourceManager.ResourceType` covers both material resources (Wood, Rock) and food resources (Seaweed, Coconut, JellyfishGuts); `ResourceManager.IsFoodType` is the single source of truth for which is which, but both kinds flow through the same `TurtleAgent.DeliverCarriedResources` path into the same `ResourceManager`/`TurtleNest` stockpile — there is no separate food building. Food's special handling happens on the way back out: while storming, `TurtleNest.SendWave` periodically pulls stockpiled food via `ResourceManager.Remove` and flies it out to eligible turtles as a buff (`TurtleNest.SpawnFoodFlight` → `TurtleAgent.ApplySeaweedBuff`/`ApplyCoconutBuff`/`ApplyJellyfishBuff`); if stock runs dry mid-storm the buff is stripped back off. `GetEligibleTurtles` skips turtles parked at a Watchtower and skips crabs entirely. Read `TurtleNest`'s class-level doc comment before touching food flow.

Per-hit yield goes through `UpgradeManager.RollHarvestAmount(type, harvester)`, which returns 1 or 2 by adding the turtle-only Barnacles chance on top of the per-type Wood/Rock double-drop chances. `ResourceNode`, `Coconut` and `JellyfishAgent` all loop that many `CollectResourceUnit` calls, breaking when the carrier is full.

### Crabs: a TurtleAgent variant, not a second agent

A crab is a Turtle prefab variant carrying a bare `CrabAgent` marker component, so selection, orders, pathfinding, harvesting, delivery and separation all come from `TurtleAgent` unchanged. Only a handful of places branch on `TurtleAgent.IsCrab`:

- `TryAcquireAggroTarget` and `TrashHealth.OnTriggerEnter2D` both gate on `TurtleAgent.CanAttackTrash` — false for a crab until the Crab Warriors card, so it neither seeks trash nor damages what it bumps.
- `UpdateIdle` holds a non-fighting crab still at the nest through a storm instead of guard-roaming.
- `UpgradeManager.ApplyTo` gives crabs only their own carry-capacity card — turtle speed, crit, and Barnacles all skip them — and `TurtleNest.GetEligibleTurtles` excludes them from night food. Environmental effects earned in the world (Campfire, Algae, Runes) still apply, since those never route through `ApplyTo`.

Prefer this shape for any future unit: a marker component plus a few `TurtleAgent` branches, not a parallel agent script.

### Audio

Sound effects are authored as `SoundEffect` fields — a plain `[System.Serializable]` class (clip variations, volume, pitch range, throttling), serialized **inline on whatever component owns the event**, not as assets or per-object `AudioSource`s. Adding a sound to something is one field plus one `sound.Play(transform.position)` call; see `ResourceNode.RegisterHarvestHit` (tree/rock impacts) and `TurtleLocomotion.FixedUpdate` (the sand push, gated on the same surface check that colors the fin particles).

`AudioManager` owns a fixed pool of 2D `AudioSource`s and all the throttling. Pooling is what lets a sound outlive its emitter (a node that depletes mid-clip, a turtle that dies) and is what makes a global voice cap possible at all. Playback is deliberately 2D — in a zoomable top-down game, real 3D falloff would swell and fade with zoom rather than with anything in the world; distance is handled instead by `SoundEffect`'s optional `Max Audible Distance` cull.

Throttling (`Min Interval`, `Max Voices`) is **shared scene-wide per sound**, keyed on the effect's first `AudioClip` — every prefab clone has its own `SoundEffect` copy but they all reference the same clip assets, so all trees share one budget while rocks get their own, with no id field to author. This matters because these events are per-hit and per-fin-stroke: without it, a dozen harvesting turtles stack a dozen copies of the same impact. `Play` is a silent no-op when no `AudioManager` is in the scene, so audio is never a hard dependency (the Menu scene runs without one).

Two volume channels, split at the source rather than by tagging sounds: `MusicPlayer` (its own dedicated looping `AudioSource`, outside the pool for the same reason `AmbienceController` is — a loop never finishes, so it would hold a pooled voice forever) answers to `GameSettings.MusicVolume`, while everything else — every pooled one-shot plus the beach/rain beds, which read `AudioManager.MasterVolume` — answers to `GameSettings.SfxVolume`. `AudioManager.MasterVolume` is now the authored mix times that setting, read live on every play so a slider drag is audible as it happens.

### Settings

`GameSettings` is a static PlayerPrefs store (same shape and same reasoning as `PlayerProgression`) holding the player's four knobs: camera drag speed, camera zoom speed, music volume, sound effects volume. The two camera values are **multipliers** over the speeds authored on `CameraController`, never absolute speeds — the tuned feel stays the 1x default, and retuning the camera in the Inspector doesn't strand every save on a stale absolute number. Values are cached in statics (they sit on hot paths — every sound played, every drag frame) and written without flushing; `Flush()` is called once when the screen closes, since a dragged slider writes every frame. Every reader polls live; there is no change event.

`SettingsMenuUI` is one panel dropped into **both** scenes that configures itself from `GameSettings` (slider ranges included) rather than being set up differently in each. One detection — does this scene contain a `GameOverUI`? — drives the only two things that genuinely differ: in gameplay it pauses (storing and restoring the previous `Time.timeScale`, so it nests correctly over TimeControlUI's 2x or an already-paused game) and leaves Escape to `GameOverUI`, which closes it ahead of closing the build drawer or pausing; in the Menu it neither pauses nor defers, and reads Escape itself. Every way out — its own close button, Escape, or the pause menu's Back button through `GameOverUI.GoBack` (same "close settings, else close the drawer, else pause/resume" decision Escape makes, taken from the same place) — funnels through `SettingsMenuUI.Close`, so the panel always leaves the same way: `UISlidePanel.PlayOut`, deactivated only once it's actually off-screen. Sharing that Back button is purely a wiring choice; it only needs the button to stay clickable, which means this panel's backdrop leaves `Raycast Target` **off** — the one full-screen graphic here where that's the deliberate setting rather than the trap. Nothing leaks through it: `IsOpen` already stands down selection, build mode and the camera, and `TimeControlUI`'s speed buttons gate on it too (they were the only other UI acting on a click without checking a phase flag). `SettingsButton` opens it through the singleton, mirroring `BuildMenuToggleButton` including the phase fade — but only in the gameplay scene, since `IsBlockedByPhase` reads statics (`GameOverUI.IsRunOver`) that the Menu scene never resets.

### Pathfinding

`PathfindingManager` wraps `AStarPathfinder` with this project's grid conventions. Its blocked-cell set is rebuilt fresh every frame (node counts are modest; this avoids invalidation bugs) and shared by every caller within that frame, while deep water is cached since it never changes after generation. `BuildBlockedCells` therefore hands back a **shared, read-only** set — never mutate it. `FindPath` used to copy it and union deep water in; both are gone, because that copied a four-figure number of cells per request. Deep water now goes to `AStarPathfinder` as a second set it tests alongside the first, and the start/goal exemptions go as cells rather than being applied by mutating a private copy. On top of that, completed routes are cached across frames (`pathCache`) keyed on start cell, goal cell and the search flags, dropped whenever the node/reef count changes or the island regenerates — and handed out as **copies**, since callers trim and stitch what they get. Inside the search, per-cell bookkeeping is flat arrays indexed off `bounds` and reused between calls, not `Vector3Int`-keyed dictionaries. Opt-in axes:

- `avoidDeepWater` — turtles pass `true` so they can never path past the shallows; trash passes `false` since it must cross open ocean.
- `allowDiagonalSqueeze` — turtles pass `true` (small enough for a genuine diagonal gap); trash keeps the strict corner guard.
- `avoidCoral` — **on by default**, so trash routes around a `CoralReef`; `TurtleAgent` passes `false` at all four of its call sites, since turtles physically pass through coral.
- `moverRadius` (`HasLineOfSight` only) — how wide the asking mover is, so line of sight rejects a segment that runs *flush past* a blocked cell and not just one that enters it. Each mover measures its own from its collider (`TurtleAgent.MeasureLineOfSightRadius`, cached in `Awake`) rather than the manager assuming a size, since a crab is a prefab variant and may differ. `0` reproduces the old zero-width-line behavior exactly.

Clearance and the diagonal squeeze deliberately coexist: when `allowDiagonalSqueeze` is on, the two flanking cells of a corner the center line legitimately crosses are exempt from the clearance test — that corner *is* the gap the flag licenses, and `FindPath` still allows it. The exemption covers only those two cells, which are always diagonal to each other, so it can never open a wall of cardinally-adjacent obstacles. Because `FindPath`'s waypoints are cell centers, a mover only fits the routes it's given while its radius stays under half a cell; past that `HasLineOfSight` logs a one-time warning telling you to use `extraObstacleInflation` (a float, on the same fractional scale as `obstacleInflationRadius`) on **both** calls rather than relying on the radius alone.

Buildings are never pathfinding obstacles — turtles pass through non-interactable ones and trash is meant to ram walls. Coral gets its trash-blocking purely from the flag above plus sitting on the Building physics layer (turtles excluded, trash not). Aggro-chasing turtles skip pathfinding via `HasLineOfSight` when a target is directly visible, since trash moves too fast for a stored path to stay accurate; that check shares `BuildBlockedCells` with `FindPath` so the two always agree.

### Input handling

Mouse/keyboard polling is spread across a few independent `Update()` loops that coordinate via the static flags above rather than a central input router: `CameraController` (drag-to-pan, scroll-to-zoom), `TurtleSelectionController` (click a turtle to select, click elsewhere to order it), `BuildModeController` (the on-screen `BuildMenuToggleButton` to enter build mode, scroll to cycle buildables, click to place), `GameOverUI` (Escape — which now means, in order: close the settings screen, else close an open build drawer, else pause). `TimeControlUI` sets `Time.timeScale` directly (0 / 1 / 2). Click-vs-drag disambiguation (a screen-pixel distance threshold plus `CameraController.WasDragging`) is duplicated between `TurtleSelectionController` and `BuildModeController` rather than shared — keep both in sync if that threshold logic changes. Both also keep their own copy of an `EventSystem.IsPointerOverGameObject` guard, latched at press, so clicking the HUD never also places a building or orders a turtle through it. **Any full-screen UI graphic must therefore keep `Raycast Target` off unless it is deliberately modal** — the EventSystem answers that guard for decorative graphics too, so an overlay left on that flag swallows every gameplay click while it's visible, with no error and no visible cause. `UpgradeSelectionUI`'s backdrop doubles as the storm-time night darkening and so toggles the flag from code (`SetBackdropBlocking`): off for the night, on only while the card pick is genuinely modal.

The build drawer is a full-height docked side panel listing **every unlocked buildable at once**, one runtime-instantiated `BuildMenuRow` each (replacing an earlier three-slot carousel). Selection is shown by inflating that row's icon while a single cost readout travels to sit level with it, its numbers counting to the new price on the same timeline — `BuildSelectionUI` positions rows itself rather than via a Layout Group, precisely because the readout has to align against a specific row's live position. Rows are rebuilt only when the unlocked *set* changes, not on every `SelectedBuildableChanged` (which also fires for price bumps). A row can be clicked or scrolled to; both route through `BuildModeController.SetSelectedIndex`, which stays the single owner of what's selected. The demolish row (see `DemolishTool` above) is one of these rows like any other — same click, same scroll — just floated to the top of the list with a separator gap and no price shown. `BuildMenuHudShift` keeps the resource counters and time controls clear of the panel by **mirroring the drawer's own `UISlidePanel.CurrentDisplacement`** rather than running a parallel animation — no distance, duration or curve to keep in step, and re-siting or resizing the drawer moves the HUD by the new amount for free. It writes nothing while the drawer is shut, which is what lets it coexist with an element's *own* `UISlidePanel` (TimeControlUI has one); it also reads its rest position from that panel's `HomePosition` rather than from a live `anchoredPosition` a sibling may already have overwritten. Two components writing one `anchoredPosition` is the hazard here — the loser is whichever ran first. `BuildMenuToggleButton` is only a handle (a hammer tab poking out of the panel) — it calls `ToggleBuildMode` and hides itself during blocking phases, nothing more; the controller owns the state and `UISlidePanel` owns the slide. Escape also closes the drawer, but that's handled in `GameOverUI`, the scene's **single reader of the Escape key**: it decides what the key means when several things could claim it (closing the drawer takes priority over pausing). Keep new Escape behavior there rather than polling the key in a new system — two readers would race on script execution order.

### Walls: static grid registry, not a component walk

`WallGrid` is a static `Dictionary<Vector3Int, WallAutoTile>` (not a MonoBehaviour singleton) that every placed `WallAutoTile` registers into on placement and unregisters from on removal, so any wall segment can look up its four neighbors and pick the correct auto-tile sprite without holding a tilemap reference or walking the scene.

### Run modifiers: opt-in hardship for a score multiplier

Picked on the menu before a run starts, in exchange for an end-of-run score multiplier — this replaced an older system that forced harmful "hazard" upgrade picks mid-run. Four parts:
- `GameModifierCatalog` — one prefab asset holding the authored list, referenced by **both** scenes so they can't drift. Registering a new modifier is one edit here.
- `GameModifierDefinition` — per-modifier presentation + score bonus; its actual effect is the `UpgradeCardDefinition` components on the same prefab.
- `GameModifierSelection` — the static PlayerPrefs read/write pair carrying the picks across the scene load.
- `GameModifierManager` — resolves the saved ids back into definitions, applies their effects in `Start` (not `Awake`, since the effect cards poke singletons only assigned in `Awake`), and exposes the multiplier for `ScoreManager.FinalizeRun`.

Multipliers **compound** rather than add; `GameModifierManager.CalculateMultiplier` is the single definition, shared with the menu's preview so the two can never disagree.

### Cross-run progression

`ScoreManager.FinalizeRun` closes out a run: applies the modifier multiplier once (not per-award, so the breakdown's numbers are exact), banks a new high score, and awards the run's score as player XP — score and XP are deliberately the same number.

`PlayerProgression` is a static PlayerPrefs store holding **only the raw lifetime XP total** — level, progress within a level, and which modifiers are unlocked are all *derived* by `ProgressionCatalog`, so retuning the XP curve re-levels existing saves instead of leaving a stored level disagreeing with it. `ProgressionCatalog` sits on the same prefab as `GameModifierCatalog` on purpose: unlock order **is** the catalog's array order. Its XP curve is an authored per-level array so any single level can be hand-tuned; it needn't reach the cap, since every level past its end costs the **largest** entry in it (largest, not last, so a dip tuned into the tail can't make the end-game accelerate). Level cap is separate, and **0 means "track the catalog"** — max level then rises on its own as modifiers are added and no level is ever left unlocking nothing. Capping *below* the catalog's length strands modifiers permanently, which `OnValidate` warns about.

### Tutorial

`TutorialManager` reads a one-shot `"TutorialEnabled"` PlayerPrefs flag set by the menu, clears it immediately, and runs a fixed scripted sequence, detecting step completion by **polling already-public state** on `TurtleAgent`/`ResourceManager`/`TurtleBed`/`DayStormCycle` rather than adding events to them. Keep that direction if you extend it. `IsActive` freezes the day clock so no storm can interrupt the scripted portion. Note the two distinct flags: `"TutorialEnabled"` is a one-shot request, while `PlayerProgression.HasCompletedTutorial` is the permanent record that unlocks the menu's modifier grid.

### Menu → GameScene → GameOver flow

`Assets/Scenes/Menu.unity` and `Assets/Scenes/GameScene.unity` are the only two scenes, both present in Build Settings (verify this if scene loads start failing in a build). **There are no `DontDestroyOnLoad` objects anywhere — PlayerPrefs is this project's only cross-scene channel**, which is why `GameModifierSelection` and `PlayerProgression` exist as static PlayerPrefs wrappers rather than persistent singletons. `SceneTransitionPanel` is per-scene for the same reason: each scene owns its own copy and reveals itself shortly after load.

`MainMenuController` owns the start screen (title, high score, tutorial toggle) and an options screen layered over it hosting `ModifierSelectionUI`; its Play button calls `StartGame`, which writes the PlayerPrefs setup and loads the gameplay scene.

`GameOverUI` handles both endings and doubles as the pause menu (Escape, only while the run isn't over). It polls `TurtleNest.Instance.IsDestroyed` rather than subscribing, since the nest is runtime-spawned after scene load. On either ending it calls `ScoreManager.FinalizeRun`, then plays two pages inside one panel frame — `ScoreBreakdownUI` animates the score line by line, then `LevelUpPanelUI` replays the XP already banked (it only *animates*; nothing there writes progress, so quitting mid-fill still keeps the levels). Restart and Menu buttons appear only once both settle.

### Dormant: multi-island runs

`IslandTransitionController` (wipe everything, regenerate the map in place, keep score and upgrades) and `DayStormCycle.AdvanceToNextIsland` still exist and still work, but **nothing calls them** — `GarbagePatch.Depleted` has no subscribers, because depleting the patch now ends the run as a win instead of moving to a new island. `UpgradeManager.RegisterPerIslandRespawn` is likewise wired up but only ever fires on the initial island generation.

Leave this intact rather than deleting it, and keep new spawn-into-the-world cards registering a per-island respawn as the existing ones do — it costs nothing today and is exactly what those cards need if multi-island runs come back.
